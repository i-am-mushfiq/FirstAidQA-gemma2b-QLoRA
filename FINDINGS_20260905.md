## Retracted claims

Raised during this review, then refuted by measurement. Recorded so they are
not re-raised, and as a check on the review's own reliability.

| Claim as raised | What the measurement showed |
|---|---|
| **The BM25 gap gate is tuned on the evaluation data it is scored on**, biasing F and G upward — four of seven patterns cite eval outcomes ("scored ≤2/5 across all configs", "V2Q37 burn cooling top-ranked gap"). | Running all seven patterns over the 41-question bank: only **2 questions are gated** (V2Q35 tourniquet, V2Q41 spinal), **0 of 11 safety-critical questions**, and **five of seven patterns never fire at all** — including `burn_cooling`, the one cited as fit on V2Q37. The gate cannot be inflating F on the SC subset. What survives is a much smaller point: F is empirically "BM25 top-1 with two questions excluded", so describing it as a seven-pattern gate oversells the mechanism, and the two gated items were chosen knowing their prior scores. |
| **The training/evaluation prompt mismatch handicaps the adapter**, so B−A understates the fine-tuning benefit. | Adapter configs mention EMS **less** than base configs (40.2% vs 59.8%); training used all four instruction prefixes at ~25% each; and the eval prompt structurally matches `template_idx 3`. No format handicap exists. The real defect is at generation time (finding 6), not training time. See 6b, 6d. |
| **The ascii encoding on the judgment writers destroys non-ASCII characters in judge rationales.** | `json.dump` defaults to `ensure_ascii=True`, so non-ASCII is escaped to `\uXXXX` before the encoder sees it; round-trip verified lossless and `errors="replace"` never fires on any JSON writer. It survives only for the three plain-text writers, where it corrupted one em dash in a generated `.tex` header. Downgraded from data loss to cosmetic. |

## Not defects — protect these

- **Gemma's chat template raises `'System role not supported'`.** `build_hf_dataset_v2` folds the system prompt into the user turn, which is the correct workaround. If someone "fixes" it to pass a `system` role, training breaks immediately.
- **The label masking in `tokenize_dataset_v2` is sound.** `add_special_tokens=False` on both the instruction and the full text keeps the boundary aligned, and the instruction is a strict prefix of the full text under Gemma's template.
- **`confirmed` in `aggregate.py` is deliberately two-sided**, as `PRECOMMIT.md:20` defines it. It was left exactly as pre-registered; direction is reported alongside it, not folded into it.
- **The eval bank has no exact overlap with any split** — the one contamination that would have been fatal is absent.

## Why this session happened, and a correction to how it started

An external audit document ("FirstAidQA · premise audit · 5 Sep 2026") was
brought in for review. It argued that the July camera-ready run was generated
under an EMS-advising prompt while being graded against offline references and
an offline rubric, and that the fix was to regenerate under
`offline_definitive_v1`.

Its central factual claim verified. Several of its supporting claims did not:
its "the rubric forbids penalising EMS" evidence quoted **Rubric A**, a rejected
candidate in Section 3 of `rubric_v2.md`, not the operative Section 6 rubric; and
its "judges almost never cite EMS (3–5%)" figure was a regex artifact that
excluded the bare token `EMS` (with it: deepseek 27.6%, claude_or 61.0%,
gpt 21.5%).

**The process error was mine.** The audit was verified against code and data, but
this register — which had already worked the same question to a *different*
conclusion (finding 6 DOWNGRADED, no regeneration required, and 6d warning
explicitly against regenerating) — was not read first. The regeneration in
§A1 below was carried out before that warning was surfaced. No API money was
spent and the July run is untouched, so nothing is lost; but the ordering should
have been the other way round.

## A1 · Finding 6d, measured

**6d as raised:** the July run generated under a prompt byte-identical to
`data_v2.SYSTEM_PROMPT`, so the model was asked at test time exactly what it was
asked in training. `offline_definitive_v1` matches neither, so generating with it
against the existing adapter creates the train/test shift that 6b retracted.
Conclusion: *do not run the offline prompt against the current adapter without
retraining.*

**The factual claim verifies exactly**, including the hashes it cites:

| prompt | sha256 | length |
|---|---|---|
| `data_v2.SYSTEM_PROMPT` (training, and July generation) | `09f68afa…` | 168 chars |
| `offline_definitive_v1` | `0d97fe5d…` | 447 chars |

So 6d's premise is correct. Its *consequence* — that this handicaps the adapter —
is an empirical question, and was treated as one rather than argued.

### Method

`prompt_shift_probe.py` (new, committed). Same adapter
(`10cat_4bit_r16_lr1e-4_p3_v2_20260508_054337`), same 41 questions, same greedy
decoding and `DECODING_PARAMS`, same `max_new_tokens`. **Only the system prompt
differs.** The offline arm is read from the verified run
`CAMERA_READY_OFFLINE_20260905_204533`; the training-prompt arm is generated by
the probe. Output: `evaluations/prompt_shift_probe.json`.

### Control: the probe reproduces July

The training-prompt arm should behave like July's config B, because it is the
same prompt against the same adapter. It does, to the decimal:

|---|---|---|
| July `B_FINETUNED_4BIT` | 41.7 | 50.4 |

### Result

| metric | TRAINING prompt | OFFLINE prompt |
|---|---|---|
| mean words | 41.7 | 42.8 |
| mean tokens | 50.4 | 52.0 |
| mean ROUGE-L vs reference | 0.1587 | **0.1603** |
| EMS mentions / 41 | 7 | **2** |

Answer-to-answer similarity: mean Jaccard 0.484, median 0.500, 0/41
byte-identical.

### Reading

- **No length collapse.** 41.7 → 42.8 words. The model is not destabilised by an
  instruction it never saw in training.
- **No proxy-quality penalty.** ROUGE-L moves **+0.0016 in the offline arm's
  favour**. The predicted handicap is not visible; if anything the sign is the
  wrong way for 6d.
- **The model complies rather than being confused.** EMS mentions fall 7 → 2.
  It read the new instruction and followed it. That is the behaviour of a model
  responding to a prompt, not one thrown by it.
- **The wording genuinely differs** (Jaccard 0.48), so this is not a case of the
  prompt being ignored. The texts change; the measurable quality does not.

### Verdict on 6d

**Downgraded from a blocking objection to a disclosure.** The premise is right,
the predicted consequence is not observed on any available proxy. Retained
caveats, stated plainly:

1. ROUGE-L is a weak proxy for a judge score. This sizes the shift; it does not
   rank the two arms. Only judging is definitive, and judging has not run.
2. The measurement is on config B. Base configs (A, G) and the technique configs
   were not probed.
3. The train/test prompt shift is *real* even though it appears costless. It
   belongs in the limitations section either way: the adapter was trained under
   one system prompt and evaluated under another.

**Consequence:** the offline run may proceed to judging. 6d's instruction not to
regenerate is not upheld by measurement, but its underlying observation should be
disclosed rather than dropped.

## A5 · Reference bank revision — recorded for disclosure

Not a defect; a change of instrument that must be disclosed with its date
ordering.

The 41 reference answers were compressed from a median of **102 words to 54**
(mean 101.5 → 53.7, range 82–125 → 43–71) and **approved by three medical
professionals**, including the abdominal-to-chest-thrust correction in §A4/54.

deletion log is held outside the repository.

run, and the offline run was regenerated afterwards so that `run.json`, ROUGE-L
and the bank hash all reflect the approved references.

**Consequences to carry into the write-up:**

- The compression widens the fine-tuned-vs-base gap on ROUGE-L for a reason

  planted references scored 5 in 39/39 — effectively a 0–4 scale. Shorter
